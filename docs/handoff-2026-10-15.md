### What fails or is unproven in the matrix

These are the rows that keep item 6 open, from the
[matrix README](../bench/results/mac-app-matrix/README.md#environment-and-matrix):

- **Fail: peer change notifications.** Seven remote operations raise no FSEvents or kqueue event
  within 5 s. Zed and Cursor keep stale buffers until close and reopen.
- **Fail: Finder silently drops a resource fork over 64 KiB** on copy, duplicate and copy-out
  (protocol §4.8's 64 KiB xattr limit).
- **Fail: positional reads of any resource fork.** A 17-byte fork reads at position 0 and returns
  `EINVAL` at 1, 17 and 18. `copyfile`'s `COPYFILE_XATTR` and `COPYFILE_ALL` fail even for tiny
  forks. FSKit's `XattrHandler` is given no position, so the module can't fix it.
- **Fail: SQLite's `-shm` file.** It differs from its server copy in 43 bytes after drain. The
  `.db` itself is correct.
- **Unsupported: native Versions** (`NSFileVersion`, Cocoa error 512). Apps warn and save
  anyway.
- **Partial:** TextEdit, Preview, Numbers, QuickTime, Zed and Cursor, each for a reason named in
  its row.
- **Untested:** two independent Macs, Premiere, Final Cut, Resolve, Microsoft Office and Photos.
  Under the matrix's scoring, untested is not a pass.

Step 5 is done when a writable drive from the shared core works in Finder and the target apps, a
signed and notarized app brings it back at login, and a 50 GB video project and a code repo work
across **two Macs** with changes visible within 5 s. No exit criterion has been waived.

## 2. How work is done here

The earlier slices kept to these rules. Keep to them.

- **Commits:** sign off every commit (`git commit -s`, DCO). New source files start with
  `// SPDX-License-Identifier: Apache-2.0`. Name the area first in commit subjects:
  `client:`, `daemon:`, `macos:`, `cli:`, `tests:`, `bench:`, `docs:`.
- **One fix per PR.** #62–#65 were each a single, separately tested fix. #66 carried evidence and
  depended on them. When PRs stack, say the merge order in each description.
- **Spec changes:** anything a client, server or stored drive could observe needs an RFC
  (`rfcs/0000-template.md`, next number 0006) before code. Then the implementing PR adds spec
  text, at least one conformance case and a `spec/CHANGELOG.md` entry.
- **Validation before every push** (CI runs the same on Ubuntu, Rust only):

  ```bash
  cargo clippy --workspace --all-targets --locked -- -D warnings
  cargo test --workspace --locked
  python3 spec/conformance/validate.py
  python3 tests/bench/credentials_scripts.py
  cargo build -p voidfs-server -p voidfs-conformance && tests/interop/run.sh memory   # also fs, versitygw
  ```

  CI also runs interop on MinIO, Docker Compose, and on `main` the GC model and a small
  benchmark.
- **Prove every new test.** Each new test must be seen failing with its code broken, one break
  at a time, and the breaks recorded in a `breaks-*.log` next to the evidence (39 for item 4).
- **Evidence:** each slice puts a README plus `raw/` output under `bench/results/<topic>/`, with
  replay commands. The step doc links to it, and PARITY's step 5 status gets a dated entry.
- **Scoring:** pass, partial, fail or untested, as the matrix README defines them. Never turn a
  known limitation into a pass. A substitute app (LibreOffice, Blender, AVFoundation) has its own
  row and certifies nothing else.
- **Mac hygiene:** run test daemons in a `mktemp` state directory and point the agent at it with
  the `VoidfsStateDirectory` default. Never write to `~/Library/Application Support/voidfs`, and
  never replace `/Applications/voidfs.app`. After a run, restore the registrations and defaults as
  the matrix README's "Preparing and restoring the isolated rig" section says, and record the
  cleanup.
- **Stops:** when a choice changes the plan's policy (a names rule, a durability promise, the
  adapter default, an untested row), ask the user once, record the answer in the step doc, and
  continue.
- **Where work can run:** Rust core, daemon, CLI and SDK work builds and tests on Linux. Swift,
  FSKit, the app and every matrix row need the development Mac: macOS 27.0.1 (26A434), Xcode 27
  beta (27A5194q), Apple M5 Pro. The agent sandbox there blocks FSEvents, file coordination and
  daemon sockets, so run those rows outside it.

### Task 2. Root-cause the SQLite `-shm` divergence

[`sqlite-shm-byte-diff.json`](../bench/results/mac-app-matrix/raw/sqlite-shm-byte-diff.json):
after publication drained, the mount's `wal.db-shm` holds a full WAL-index header (offsets 0–95,
both copies), while the server's copy has only the first word and zeros, 43 bytes apart. SQLite
writes `-shm` through a shared `mmap` and never calls `msync` on it. Two explanations fit, and
they mean different things:

- **(a) The stores never reached the module.** They sat in the kernel's pages, which a read
  through the mount would also show. Item 4 measured that `msync`, the last close, `sync(2)`, the
  periodic sync and unmount push a mapping's pages
  (`apps/macos/FSModule/VoidfsVolume.swift`, `push(_:)`), and that the volume pushes before an
  open. A mapping that stays alive with no further opens may never be pushed. If so, this is a
  durability gap for *any* app that holds a shared writable mapping, and the step 5 durability
  table overstates what is on disk.
- **(b) The stores reached the module and were staged, but nothing published them.** For
  example, the quiet-period or close flush doesn't fire for writes that arrive only as page
  pushes. That is a core or queue bug.

Steps:

1. Write a minimal C probe next to `bench/results/mac-fskit-writable/mmapseq.c` that copies
   SQLite's pattern: `open(O_RDWR)`, `ftruncate` to 32 KiB, `mmap(MAP_SHARED)`, stores, no
   `msync`, the descriptor kept open past the 2 s quiet period, then each close and `munmap`
   order. Run it on a mount with `-o trace`.
2. For each case, compare three views: the kernel's (`read(2)` through the mount), the
   daemon's staged bytes (a second session, or the stage file in the test state directory), and
   the server's (`mount_metadata` or an SDK `GET`). The trace shows whether write callbacks
   arrived.
3. For (a): measure a push of mapped files' pages on the volume's own timer or before the
   session's 2 s flush, and what it costs. Don't change the grant away from writeThrough (item 4,
   Q2). Ask the user before changing the durability table.
   For (b): fix it in `crates/voidfs-client` with a regression test in `tests/mount_writes.rs`
   or `tests/mount_publication.rs`, and prove the test by breaking the fix.
4. Then rerun the SQLite row (`apps/macos/scripts/app-matrix.py --row sqlite`).

Separately, SQLite rebuilds `-shm` from the WAL and never needs it for recovery. Treating
`*-shm` as local housekeeping, like `.DS_Store` (`local_only` in
`crates/voidfs-client/src/mount.rs`), would be a change to the accepted names policy, which lists
`-shm` as an ordinary file. Put that to the user **after** the root cause is known, not as a
substitute for it.

**Done when:** the probe shows the defect before the fix and passes after it (or shows it can't
happen, with the trace). The SQLite row's strict `-shm` equality passes, or the user has made a
recorded names-policy decision. The step doc's durability table is still true.

### Task 4. Investigate remote change notifications

Apps that watch the filesystem (editors, Xcode, build tools, `git status` helpers) never hear
about another machine's changes. Revokes from `setCacheState` don't raise FSEvents or kqueue
events. Before treating this as permanent:

1. Search the macOS 27 SDK's FSKit headers for a module-initiated notification
   (`xcrun --show-sdk-path`, then `FSKit.framework/Headers`: look for notify, event, kqueue,
   change). Record the answer either way.
2. Measure whether smbfs raises FSEvents and kqueue events when the server sends change
   notifications. Use the SMB spike's server (`bench/results/mac-smb-spike/smbspike.py`) and
   `apps/macos/scripts/watch-events.swift`. This bears directly on the FSKit-or-SMB decision.
3. Only as a measured experiment, not a plan: whether an idempotent kernel-visible operation
   through the mount (setting an unchanged mtime, say) raises an event that apps act on. Any such
   idea must create no version and must not race a real local write. Expect to reject it.
4. If there's no API, add a Feedback draft (task 5).

**Done when:** a dated note in the step doc records the SDK answer, the SMB measurement and any
experiment, and the user has the facts to decide whether this changes the 12 October FSKit
decision.

### Task 6. RFC 0006: xattrs over 64 KiB

Protocol §4.8 caps a file's xattrs at 64 KiB total (`413 EntityTooLarge`) and calls more a future
feature. On FSKit, Finder copies a file with a larger resource fork, reports success and drops
the fork. That alone fails item 4. Write `rfcs/0006-large-extended-attributes.md` from the
template (status Proposed) and answer:

- Where large values live: inline in the commit log as now, or content-addressed like file data
  (shards plus a descriptor), and above what size.
- The new limits per value and per object, and what `GET ?x-voidfs-attrs` and listings with
  attributes (§4.9) return for a large value. Inline, by reference, or fetched separately?
- Versioning (still one `attrs` version per change), forks, restore, and GC reachability for
  any value stored as shards (format §12, RFC 0002).
- Feature negotiation, so an old server refuses cleanly and an old client doesn't misread.
- The conformance cases and the `spec/CHANGELOG.md` entry the implementation will add.

State that it doesn't fix the small-fork positional-read failure (task 5). Leave "a `PUT` that
carries xattrs" (so `com.apple.provenance` stops costing an `attrs` version on every new file)
to its own RFC under item 9. It needs measurements first.

**Done when:** the RFC PR is open with no unanswered design question, and the user accepts or
rejects it. Implementation is a later PR: spec, conformance, server, `voidfs-client` mount core
and the Swift volume, then the Finder large-fork row rerun.

### Task 8. Item 7: `/Volumes`, launch services, credentials

Plan: [item 7](step-5-macos.md#item-7-volumes-launch-services-and-credentials). Suggested slices,
one PR each:

1. **Credentials in the Keychain.** The daemon's connection is in `<state>/daemon.json`, readable
   only by its user (`crates/voidfs-daemon/src/settings.rs`). `void daemon start` writes it so a
   launchd-started daemon needs no secret in its plist. Move the secret into a shared Keychain
   item that the daemon, the CLI and the app read, migrate an existing `daemon.json` once, and
   keep a fallback for a terminal-only install. Nothing secret goes in mount URLs (already
   `voidfs://<drive>`), arguments, status output or logs. Add a test that checks them.
2. **Bundled services.** Ship the Rust daemon and the Swift agent in the app and register them
   with `SMAppService`. Handle the disabled and approval-required states, guide the user to
   enable the FSKit extension, and define how the app takes over from a terminal
   `void daemon install` without two daemons (they share one store, as item 2 decided). The
   matrix README notes a Developer ID agent launch constraint that sometimes needs a Login Items
   toggle or a re-login. Reproduce it and handle it, and don't reset security settings to hide
   it.
3. **`/Volumes`.** FSKit mounts there need the `fskit.mount` entitlement or a privileged helper.
   Find out which one voidfs's team can get. A helper may only create and validate mountpoints
   and mount or unmount voidfs volumes. It authenticates its caller, checks for symlinks and
   races, and never touches bucket access or the journal.
4. **Login restoration.** Remembered mounts come back after logout and reboot, and a busy eject
   loses no acknowledged write.

**Done when:** item 7's done-when holds, with the authorization-failure, helper-absent,

## 6. Traps the last slices hit

- **Fixtures that publish during setup** race the background publisher. Keep the queue paused
  until fixture writes finish, then resume and settle (#62).
- **Timing assertions flake on CI.** Assert counts (a bounded hold happened N times), not sums of
  scheduling gaps (`9269cb4`, carried in #64).
- **Test restarts must wait for the store to be let go.** A disk flush can hold it briefly after
  a session drops (`ba6d08b`).
- **A large `target/` on the Mac** (810,885 files in `target/debug/deps`) made crash-test child
  processes slow to read root certificates. Use a fresh `CARGO_TARGET_DIR` there.
- `stop_cancels_stalled_bootstrap_and_creators_waiting_for_the_registry` **failed once under
  load** (item 3) and passed 13 times after. Watch for it, and don't paper over it.
- **boto3 isn't installed on the Mac.** Interop skips it there, and CI covers it.
- **Test pools need `multi-object-versions`** (RFC 0004). Without it, a folder restore leaves the
  mount answering `ESTALE`.
- **Killing the extension with a file open leaves a dead FSKit mount** (`EIO` everywhere).
  `void daemon restart` unmounts it with `-f` and mounts again.
- **Multipart can't carry an absence guard.** A new mounted file over the threshold goes through
  the streamed guarded `PUT` (#65). Don't route it back to multipart.
- **Drive scopes have two spellings.** CLI imports queue by alias, mounted saves by stable ID.
  Any new per-drive control must resolve both (#64).
